# RFC 0007 Amendment 1 — latest-head vs signing-key freshness

- **Outcome:** docs-only RFC amendment proposal. No product code.
- **Date:** 2026-09-15
- **Authoritative text:** `rfcs/0007-audit-ledger-freshness-anchor.md` (Amendments §)
- **Status:** RFC 0007 remains **Draft**. Amendment 1 is **proposed, not
  accepted**.
- **Product gates:** RP1-06 **not** claimed. Runtime Phase 1 product

This note summarizes Amendment 1 for handoff. It is not itself an RFC.

---

## Problem (F09 / RP1-06)

The v0.1 `ledger.head` sidecar rejects a ledger that lags a **newer** anchor
on disk. It does **not** reject restoring an **old** `ledger.json` and **old**
`ledger.head` from the same snapshot: both verify. Protecting the device
signing key from a ledger-only writer is therefore **not** the same as
protecting **latest enrolled head/generation**.

Runtime Phase 1 guide (branch `docs/runtime-phase-1-guide`, PR #149) records
this under F09 and RP1-06; implementation waits on this amendment.

---

## What Amendment 1 adds (normative Target)

1. **Two domains:** signing-key integrity vs latest-head / monotonic
   `freshness_generation`.
2. **Enrolled state** outside the roll-backable workspace tree only (or
   documented residual while co-located).
3. **Fail closed:** generation downgrade, missing enrolled record after
   enrollment, and paired tree restore when generation survives elsewhere →
   **limited recovery**, not silent accept of stale head.
4. **Authority coupling (RFC 0003):** consumed/revoke/dispatch state must be
   generation- or recovery-invalidated; audit chain verify ≠ fresh authority.
5. **Whole-device rollback:** still Research / out of scope.

v0.1 anchor format and existing conformance test names stay valid as the
conditional slice.
